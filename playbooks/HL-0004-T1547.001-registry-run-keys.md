# Playbook HL-0004 — Registry Run Key Persistence

| Field | Value |
|---|---|
| Hypothesis ID | HL-0004 |
| ATT&CK | **T1547.001** Boot or Logon Autostart Execution: Registry Run Keys / Startup Folder · related: **T1112** Modify Registry |
| Tactic(s) | Persistence, Privilege Escalation, Defense Impairment |
| Platforms | Windows endpoints and servers |
| Difficulty | Beginner — small result set, one consumer-app look-alike |
| Queries | [Sigma](../queries/sigma/hl-0004_registry_run_keys.yml) · [KQL](../queries/kql/hl-0004_registry_run_keys.kql) · [SPL](../queries/spl/hl-0004_registry_run_keys.spl) |

---

## 1. Intelligence basis

Run and RunOnce keys are the oldest and still one of the most common Windows persistence mechanisms. Commodity loaders, RATs, infostealers and ransomware operators all use them because a per-user (`HKCU` / `HKU\<SID>`) Run value needs **no administrative rights** and survives reboots. Recurring tradecraft:

- Value data pointing at a payload in **`%APPDATA%`, `%TEMP%`, `C:\ProgramData` or `C:\Users\Public`**.
- Value data that launches a **script host or LOLBin** (`powershell -w hidden ...`, `mshta http://...`, `rundll32 <dll>,<export>`, `regsvr32 /i:http...`, `wscript`).
- **Masquerading value names** that borrow a trusted product name (`OneDriveUpdate`, `SecurityHealth`, `GoogleUpdate`) while pointing at a file that product never ships.
- Writes made by `reg.exe`, PowerShell, or the malware itself rather than by an installer.

Map this to your own PIRs by citing the specific report or advisory in your hypothesis card.

## 2. Hypothesis

> If an adversary has established logon persistence through registry autostart keys in our Windows estate, we expect to see **Run / RunOnce value writes** whose data points to a **user-writable or staging path** or launches a **script host or LOLBin**, often with a **value name that does not match the binary it launches** and written by an **unexpected process**, in registry telemetry during the last 14–30 days.

**Refuted if:** registry-set telemetry for the Run / RunOnce keys covers ≥ 90% of in-scope hosts for the window, and every hit is attributed to a known, signed, user- or IT-installed application.

## 3. Data sources

| Source | Event / table | Key fields |
|---|---|---|
| Sysmon | Event ID 13 (Registry value set) | `TargetObject`, `Details`, `Image`, `User` |
| Windows Security | Event ID 4657 (requires SACLs on the Run keys) | `ObjectName`, `ObjectValueName`, `NewValue`, `ProcessName` |
| Microsoft Defender XDR | `DeviceRegistryEvents` (`ActionType == "RegistryValueSet"`) | `RegistryKey`, `RegistryValueName`, `RegistryValueData`, `InitiatingProcessFileName`, `InitiatingProcessAccountName` |
| Point-in-time | Sysinternals Autoruns / EDR live response | Current autostart entries with signature status |

**Pre-check:** confirm your Sysmon configuration actually includes the Run / RunOnce keys under both `HKLM` and `HKU` (many community configs do, but trimmed configs often drop `HKU`). Security 4657 only fires where auditing SACLs exist on the keys. If neither source covers per-user hives, log the outcome as **Inconclusive (data gap)** and consider a one-off Autoruns sweep.

## 4. Hunt steps

1. **Run the query** for your platform across the hunt window. The query extracts the launched image (`PayloadImage`) from the value data and flags values whose **name does not appear in the data** (`NameNotInData`).
2. **Stack by value name and payload image.** Sort ascending by host count. A consumer app installed by several users appears on several hosts with the same name and image; a dropper usually appears once.
3. **Compare name, path and writer.** A value called `OneDrive*` should launch `OneDrive.exe` from the OneDrive folder, written by OneDrive or its installer. Any mismatch between the three is the lead.
4. **Check the writer process and account.** Installers, updaters and the application itself are normal writers. `powershell.exe`, `cmd.exe`, `reg.exe`, `rundll32.exe`, `mshta.exe` or an Office application writing a Run value is not.
5. **Pivot** on suspicious hits:
   - The payload file: creation time, writer, hash, signature (Sysmon 11 / `DeviceFileEvents`, `DeviceFileCertificateInfo`).
   - Process tree of the writer: what ran in the minutes before (HL-0001, HL-0008)?
   - Other persistence on the same host at the same time (HL-0003 scheduled tasks, new services).
   - Execution of the payload at next logon (process creation with `explorer.exe` or `userinit.exe` as parent) and its network activity.
6. **Classify** each cluster as malicious, suspicious, or benign and record it in the hunt report.

## 5. Known benign sources (tune, don't ignore)

| Source | How to recognize |
|---|---|
| Per-user consumer and collaboration apps (Spotify, Discord, Zoom, Slack) | Value name matches the product, image is the product's own signed binary in its own `AppData` folder, writer is the app itself, appears for several users |
| Microsoft per-user apps (Teams, OneDrive) | Install under `AppData\Local\Microsoft\...`; usually does not match this rule |
| Vendor updaters using RunOnce | Signed installer writer, `C:\ProgramData\<Vendor>\` path, value removed after next logon |
| Endpoint management agents | Management agent writer, consistent across a deployment wave, change record |

Exclude by **value name + signed image path pattern + writer** together, never by `\AppData\Roaming\` alone; that path is where most per-user malware lives.

## 6. Triage questions

- Does the value name describe the binary it launches, or borrow a trusted product name?
- Is the payload signed, and by the vendor the name implies? When was it first seen in the estate?
- Which process wrote the value, and does that process normally install software?
- Is the entry present for one user (targeted) or many (likely an installed app)?
- Did the payload execute at a later logon, and did it reach out to the network?

## 7. Operationalize

- Promote the Sigma rule to production after adding scoped exclusions from step 5.
- Add a companion detection for Run values written by script hosts or `reg.exe`, regardless of the data path.
- Recommend application control (WDAC, AppLocker) rules that block execution from `%APPDATA%` and `%TEMP%` for non-allowlisted binaries.
- Schedule a periodic Autoruns or EDR autostart inventory to catch entries written before telemetry existed.
- Record outcome, detections created, and data gaps in `templates/hunt-report.md` and `templates/intel-feedback.md`.

## Lab notes

The lab dataset (`data/lab`) covers five days of "Northwind Labs" telemetry. For this hunt:

- Most Run values in the lab are written by everyday collaboration and security software and should not match.
- Expect **at least one benign look-alike**: a user-installed application that legitimately lives in `AppData\Roaming` on more than one workstation. Be ready to explain why it is benign.
- Expect at least one value whose **name and payload disagree**. Look closely at which process wrote it and what was happening on that host in the preceding minutes.
- Lab registry events come from Sysmon EID 13 and `DeviceRegistryEvents` only; there is no 4657 data.
- Set the lookback to cover early October 2026 (KQL `3650d`, SPL `earliest=0`).
