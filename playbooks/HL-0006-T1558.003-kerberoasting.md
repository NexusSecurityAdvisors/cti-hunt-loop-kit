# Playbook HL-0006 — Kerberoasting

| Field | Value |
|---|---|
| Hypothesis ID | HL-0006 |
| ATT&CK | **T1558.003** Steal or Forge Kerberos Tickets: Kerberoasting · related: **T1078.002** Valid Accounts: Domain Accounts |

| Platforms | Active Directory domain controllers |
| Difficulty | Intermediate — needs DC audit policy and an understanding of Kerberos encryption types |
| Queries | [Sigma](../queries/sigma/hl-0006_kerberoasting.yml) · [KQL](../queries/kql/hl-0006_kerberoasting.kql) · [SPL](../queries/spl/hl-0006_kerberoasting.spl) |

## 1. Intelligence basis

Any authenticated domain user can request a Kerberos service ticket (TGS) for any account with a Service Principal Name. Part of that ticket is encrypted with the service account's password hash, so it can be cracked offline with no further contact with the domain. Kerberoasting is a staple of ransomware affiliates and intrusion sets because:

- It needs only a normal user's foothold (`Rubeus kerberoast`, Impacket `GetUserSPNs.py`, PowerView `Invoke-Kerberoast`).
- Tools request **RC4-HMAC (0x17)** tickets by default because RC4 is far faster to crack than AES.
- Service accounts are often old, over-privileged (backup, SQL, SharePoint) and have weak, non-rotating passwords.

The cracked service account is then used for lateral movement (see HL-0005, HL-0009). Cite the specific report that motivates the hunt in your hypothesis card.

## 2. Hypothesis

> If an adversary is Kerberoasting in our domain, we expect to see **successful 4769 events with `TicketEncryptionType 0x17` for user-backed SPNs**, where a **single requesting account and source IP asks for many distinct SPNs in a short window**, usually from a workstation, in domain controller Security logs during the last 14–30 days.

**Refuted if:** 4769 auditing is enabled on all DCs for the window, and every RC4 service ticket maps to a documented legacy application (one stable SPN, server source, regular schedule).

## 3. Data sources

| Source | Event / table | Key fields |
|---|---|---|
| Windows Security (DCs) | Event ID 4769 (Kerberos service ticket requested) | `TargetUserName` (requester), `ServiceName`, `TicketEncryptionType`, `Status`, `IpAddress` |
| Microsoft Sentinel | `SecurityEvent` (EventID 4769) | same as above, plus `Computer` (the DC) |
| Microsoft Defender for Identity | `IdentityLogonEvents`, alerts | Defender for Identity raises its own Kerberoasting alerts — compare |
| Active Directory | `servicePrincipalName`, `msDS-SupportedEncryptionTypes`, `pwdLastSet` | which accounts are roastable and how weak |

**Pre-check:** 4769 is only logged when **Audit Kerberos Service Ticket Operations** (Advanced Audit Policy > Account Logon) is set to *Success* (and ideally *Failure*) on **every** domain controller. It is high-volume, so it is often disabled or filtered at the forwarder. If any DC is missing, record the outcome as **Inconclusive (data gap)** for that DC.

## 4. Hunt steps

1. **Run the query** for your platform. It keeps successful (`Status 0x0`) RC4 tickets and drops machine accounts (`$`) and `krbtgt`, mirroring the Sigma rule.
2. **Stack by requesting account + source IP** and count **distinct SPNs**. Many distinct SPNs in a few minutes is the lead. A single steady SPN requested from a server every few hours is the legacy-application pattern.
3. **Measure the burst.** Compare `SpanMinutes` and `ActiveHours` with `DistinctSPNs`: roasting tools request every SPN at once, so expect several SPNs within one or two minutes.
4. **Resolve the source IP** to a host (DHCP, `DeviceNetworkInfo`, 4624 on that host). Is it a workstation or a server? Who was logged on?
5. **Pivot to the requested service accounts.** Check `pwdLastSet`, group membership, and `msDS-SupportedEncryptionTypes` for each. Then search for **logons by those accounts** (4624 types 3 and 10) after the burst, especially from the requester's workstation — that is the cracked credential being used.
6. **Pivot to the endpoint.** On the requester's host, look for tooling: `Rubeus.exe`, `GetUserSPNs`, PowerShell with `KerberosRequestorSecurityToken`, `Invoke-Kerberoast`, or LDAP queries for `servicePrincipalName=*`.
7. **Classify** each cluster and record it in the hunt report.

## 5. Known benign sources (tune, don't ignore)

| Source | How to recognize |
|---|---|
| Legacy RC4-only applications or appliances | One SPN, the same server source IP, regular schedule over days |
| Service accounts without AES configured | `msDS-SupportedEncryptionTypes` unset/RC4; fix the account rather than excluding it |
| Cross-forest / trust referrals and older clients | Consistent client population, trust-related SPNs |
| Authorized red-team or AD assessment tooling | Named assessment account, scoped engagement window, written authorization |

Scope exclusions to **requester + source IP + SPN**. Excluding all RC4 tickets for a service hides the next attacker who roasts it.

## 6. Triage questions

- How many distinct SPNs did this account request, and over how many minutes?
- Is the source IP a workstation or a server? Does the requester normally use that service at all?
- Are the requested accounts privileged (backup, SQL, admins)? When were their passwords last set?
- Did any of the requested service accounts log on somewhere new after the burst?
- Is there an RC4 dependency documented for this SPN, or is RC4 just never disabled?

## 7. Operationalize

- Promote the Sigma rule with a scoped exclusion for each documented legacy SPN; alert on **≥ 3 distinct SPNs per requester within 10 minutes** as the high-fidelity variant.
- Set service accounts to **AES only** (`msDS-SupportedEncryptionTypes` = 0x18) and plan the domain-wide removal of RC4; once done, any 0x17 ticket becomes an alert by itself.
- Move services to **gMSA** (120-character managed passwords, automatic rotation). For accounts that cannot move, enforce **25+ character random passwords** and rotate them.
- Deploy a **honeypot SPN**: a realistic-looking service account with an SPN, a long random password, and no legitimate use. Any 4769 for it is a high-confidence alert.
- Remove unnecessary SPNs and audit service accounts in privileged groups.
- Record outcome, detections, and data gaps in `templates/hunt-report.md` and `templates/intel-feedback.md`.

## Lab notes

- The lab includes five days of 4769 events from a single domain controller, in both Sentinel (`SecurityEvent`) and raw Security log format.
- Most tickets are AES; machine-account RC4 tickets exist and are filtered by the query. Confirm you agree with that filter.
- Expect one RC4 pattern that runs every day and needs a business explanation, and one that does not look like the others at all.
- The requester's `TargetUserName` carries a realm suffix and `IpAddress` an IPv4-mapped IPv6 prefix; both are normalized in the queries. Map the source IP back to a host name.
- Once you know which service accounts were requested, follow them forward in time — at least one shows up again in the lateral-movement and RDP hunts.
