# Playbook HL-0003 — Scheduled Task Persistence

| Field | Value |
|---|---|
| Hypothesis ID | HL-0003 |
| ATT&CK | **T1053.005** Scheduled Task/Job: Scheduled Task |
| Tactic(s) | Execution, Persistence, Privilege Escalation |
| Platforms | Windows endpoints and servers |
| Difficulty | Beginner — clear signal, one vendor look-alike to explain |
| Queries | [Sigma](../queries/sigma/hl-0003_scheduled_task_persistence.yml) · [KQL](../queries/kql/hl-0003_scheduled_task_persistence.kql) · [SPL](../queries/spl/hl-0003_scheduled_task_persistence.spl) |

---

## 1. Intelligence basis

Scheduled tasks are one of the most reliable persistence and privilege-escalation mechanisms on Windows, and they appear in almost every ransomware and intrusion report. Recurring tradecraft:

- `schtasks.exe /create` with an action (`/tr`) pointing at a payload staged in **`C:\ProgramData`, `%APPDATA%`, `%TEMP%` or `C:\Users\Public`**.
- Actions that launch a **script host or LOLBin** (`powershell`, `mshta`, `rundll32`, `regsvr32`, `wscript`, `cmd /c`) or a remote URL.
- **Masquerading**: task names placed under `\Microsoft\Windows\...` to blend in with built-in tasks, binaries named `svchost.exe` or `update.exe`, and triggers such as `/sc onlogon` or `/sc onstart` with `/ru SYSTEM`.
- Remote task creation (`/s <host>`) as a lateral-movement and execution primitive.

Map this to your own PIRs by citing the specific report or advisory in your hypothesis card.

## 2. Hypothesis

> If an adversary has established persistence or escalated privileges through scheduled tasks in our Windows estate, we expect to see `schtasks.exe` **task-creation** events whose action runs from a **user-writable or staging path**, invokes a **script host or LOLBin**, or whose task name **masquerades under `\Microsoft\Windows\`**, created by **unusual parents or accounts**, in endpoint telemetry during the last 14–30 days.

**Refuted if:** process-creation telemetry covers ≥ 90% of in-scope hosts for the window, task-registration events (4698 or TaskScheduler 106) were reviewed for tasks created without `schtasks.exe`, and every hit is attributed to a documented vendor or administrative source.

## 3. Data sources

| Source | Event / table | Key fields |
|---|---|---|
| Sysmon | Event ID 1 (Process Create) | `Image`, `OriginalFileName`, `CommandLine`, `ParentImage`, `User` |
| Windows Security | Event ID 4688 (requires command-line auditing) | `NewProcessName`, `CommandLine`, `ParentProcessName` |
| Windows Security | Event ID 4698 (A scheduled task was created; requires *Audit Other Object Access Events*) | `TaskName`, `TaskContent` (full task XML: action, trigger, principal) |
| Task Scheduler Operational | Event ID 106 (Task registered) | `TaskName`, `UserContext` |
| Microsoft Defender XDR | `DeviceProcessEvents`; `DeviceEvents` (`ActionType == "ScheduledTaskCreated"`) | `ProcessCommandLine`, `InitiatingProcessFileName`, `AdditionalFields` |

**Pre-check:** the Sigma, KQL and SPL queries only see tasks created **through `schtasks.exe`**. Tasks registered through the COM API, PowerShell `Register-ScheduledTask`, WMI, or by dropping XML into `C:\Windows\System32\Tasks` are visible only in 4698 / 106 / EDR task events. If neither process command lines nor task-registration events are collected, log the outcome as **Inconclusive (data gap)**.

## 4. Hunt steps

1. **Run the query** for your platform across the hunt window. The query extracts `TaskName`, `TaskAction` (`/tr`) and `RunAs` (`/ru`) from each command line.
2. **Stack by task name and action.** Sort ascending by host count: a task created on one host is a better lead than one created on forty. Vendor tasks are usually identical across many hosts.
3. **Read the action.** Ask where the binary lives, whether it is signed, and whether its name matches its location (a `svchost.exe` outside `System32` is never legitimate).
4. **Check the creator.** Compare `InitiatingProcessFileName` / `ParentImage` and the account. Signed installers and software-distribution agents running as SYSTEM are normal; `powershell.exe`, `cmd.exe`, `wmiprvse.exe` or an Office application creating a SYSTEM task from a user session is not.
5. **Pivot** on suspicious hits:
   - The action binary: when was it written (Sysmon 11 / `DeviceFileEvents`), and by what process?
   - Task execution: TaskScheduler 200/201 and child processes of `svchost.exe -k netsvcs -p -s Schedule` running the action path.
   - Other persistence on the same host in the same minutes (HL-0004 Run keys, new services 7045).
   - Same task name or action path on other hosts (spread).
   - The full task XML from 4698 `TaskContent` or `C:\Windows\System32\Tasks\<path>`.
6. **Classify** each cluster as malicious, suspicious, or benign and record it in the hunt report.

## 5. Known benign sources (tune, don't ignore)

| Source | How to recognize |
|---|---|
| OEM support and update agents (Dell, HP, Lenovo) | Signed vendor installer parent, SYSTEM, identical task name and action across many hosts, action in `C:\ProgramData\<Vendor>\` |
| Browser and application updaters | Signed updater parent, action in `Program Files`; usually does not match this rule at all |
| Software distribution (SCCM, Intune, RMM) | Management agent parent, deployed in waves that line up with change records |
| Admin scripts | Named admin or service account, scripts in a controlled share or `C:\Scripts`, documented schedule |

Exclude by **task name + action path + signed parent** together, never by `schtasks.exe` or by `C:\ProgramData` alone.

## 6. Triage questions

- Does the task name match its action, or does it borrow a Microsoft or vendor name it has no business using?
- Is the action binary in a user-writable path, and is it signed by the vendor the name implies?
- What created the task, and does that parent normally install software?
- Does the task run as SYSTEM or at logon/startup when created from a standard user session?
- Is the task present on one host (targeted) or many (likely tooling)?
- Did the action run, and what did it do afterward?

## 7. Operationalize

- Promote the Sigma rule to production after adding scoped exclusions from step 5.
- Recommend enabling **Security 4698** (Audit Other Object Access Events) and the **TaskScheduler/Operational** log fleet-wide so non-`schtasks.exe` task creation is visible.
- Add a companion detection for task names under `\Microsoft\Windows\` whose action is outside `%SystemRoot%`.
- Record outcome, detections created, and data gaps in `templates/hunt-report.md` and `templates/intel-feedback.md`.

## Lab notes

The lab dataset (`data/lab`) covers five days of "Northwind Labs" telemetry. For this hunt:

- Several vendor updaters create tasks during the week. Some will not match the rule; at least one **vendor task does match** and appears on more than one workstation. You will need to explain why it is benign.
- At least one task was built to **blend in**. Read the task name, the action path and the run-as account together, not one at a time.
- The parent process and the account are the fastest way to separate the two.
- Process creation is the only scheduled-task source in the lab; there are no 4698 events. Note that as a data gap in your report.
- Set the lookback to cover early October 2026 (KQL `3650d`, SPL `earliest=0`).
