# Playbook HL-0005 — WMI & PsExec-Style Lateral Movement

| Field | Value |
|---|---|
| Hypothesis ID | HL-0005 |
| ATT&CK | **T1047** Windows Management Instrumentation · **T1021.002** Remote Services: SMB/Windows Admin Shares · **T1569.002** System Services: Service Execution |
| Tactic(s) | Execution, Lateral Movement |
| Platforms | Windows servers and endpoints (target side of the movement) |
| Difficulty | Intermediate — requires correlating process, logon, and service telemetry across hosts |
| Queries | [Sigma](../queries/sigma/hl-0005_wmi_psexec_lateral_movement.yml) · [KQL](../queries/kql/hl-0005_wmi_psexec_lateral_movement.kql) · [SPL](../queries/spl/hl-0005_wmi_psexec_lateral_movement.spl) |

## 1. Intelligence basis

Once an intruder holds a valid credential (dumped, cracked, or bought), the fastest way to move is remote execution over SMB/RPC with tools that ship with Windows or with every offensive framework:

- **Impacket `wmiexec.py`** (and Cobalt Strike / Sliver equivalents) creates a process through `Win32_Process.Create`. On the target the child appears under `WmiPrvSE.exe`. wmiexec has a near-unique fingerprint: `cmd.exe /Q /c <command> 1> \\127.0.0.1\ADMIN$\__<epoch> 2>&1` — output is written to a file on the local ADMIN$ share and read back over SMB.
- **PsExec and clones** (`PAExec`, `RemCom`, `CSExec`, Impacket `psexec.py`) copy a service binary to `ADMIN$`, register it with the Service Control Manager, and spawn commands as children of that service.
- Ransomware affiliates routinely use both in the hours before impact: WMI for discovery, PsExec to push the deployment script or encryptor to many hosts at once.

## 2. Hypothesis

> If an adversary is moving laterally with harvested credentials, we expect to see **command interpreters or script hosts spawned by `WmiPrvSE.exe`**, or **any process spawned by a PsExec-style service binary**, on servers and workstations in the last 14–30 days — typically under a **service or privileged account that does not normally administer that host**, and preceded by a **network logon (4624 type 3)** from an unexpected source.

**Refuted if:** process-creation telemetry covers ≥ 90% of in-scope hosts for the window and every hit maps to an approved admin source (jump host, management platform) with a matching change or ticket.

## 3. Data sources

| Source | Event / table | Key fields |
|---|---|---|
| Sysmon | Event ID 1 (Process Create) | `Image`, `CommandLine`, `ParentImage`, `User` |
| Windows Security | Event ID 4688 (command-line auditing required) | `NewProcessName`, `CommandLine`, `ParentProcessName` |
| Microsoft Defender XDR | `DeviceProcessEvents` | `FileName`, `ProcessCommandLine`, `InitiatingProcessFileName`, `AccountName` |
| Windows Security (pivot) | Event ID 4624, LogonType 3 | `TargetUserName`, `IpAddress`, `WorkstationName` |
| Windows System (pivot) | Event ID 7045 (service installed) | `ServiceName`, `ImagePath`, `AccountName` |
| Sysmon (pivot) | Event IDs 17/18 (named pipe), 3 (network) | `PipeName` (e.g. `\PSEXESVC`), `DestinationPort` 135/445 |

**Pre-check:** confirm process telemetry from **servers**, not just workstations — lateral movement lands on file, backup, and application servers first. Confirm System 7045 is collected centrally; many SIEMs only ingest Security. If parent-process data is missing, log the outcome as **Inconclusive (data gap)**.

## 4. Hunt steps

1. **Run the query** for your platform across the hunt window. The SCCM/MECM compliance-script path (`\CCM\SystemTemp\`) is filtered by design — confirm that filter only removes `WmiPrvSE.exe` → `powershell.exe -File C:\Windows\CCM\SystemTemp\*.ps1` running as SYSTEM.
2. **Stack by method, account, and parent.** Sort ascending: a service account or standard user executing through WMI or a PsExec service on a server it does not own is the lead. Admin accounts from the jump host will cluster.
3. **Look for the wmiexec signature.** The query flags `\\127.0.0.1\ADMIN$\__<digits>` redirection. A hit is close to diagnostic of Impacket or a port of it; review the full sequence of commands (`whoami`, `ipconfig`, `net group "Domain Admins"`, `tasklist`) as a discovery timeline.
4. **Read the PsExec children.** What did the service run? A batch file or binary from `C:\ProgramData`, `C:\Users\Public`, `%TEMP%`, or a non-standard folder is far more suspicious than a one-line admin command.
5. **Pivot to the logon (4624 LogonType 3).** On the target host, find the network logon for the same account in the seconds or minutes before the first child process. `IpAddress` / `WorkstationName` gives you the **source** host — the next place to hunt. Note other logon types for the same account in the window; the session may not be type 3.
6. **Pivot to the service install (System 7045).** For PsExec-style hits, find the service creation on the target (`PSEXESVC`, `PAExec-*`, random 4–8 character names from Impacket `psexec.py`/`smbexec.py`) and its `ImagePath`. A renamed PsExec service (`-r`) will not match the parent list — 7045 is how you catch it.
7. **Expand.** Search for the same account, source IP, and command lines on every other host in the window. Lateral movement is rarely a single hop.
8. **Classify** each cluster and record it in the hunt report.

## 5. Known benign sources (tune, don't ignore)

| Source | How to recognize |
|---|---|
| SCCM / MECM compliance & inventory | `WmiPrvSE.exe` → PowerShell from `C:\Windows\CCM\SystemTemp\`, SYSTEM, fleet-wide (already filtered) |
| Admin PsExec from jump hosts | Named admin account, 4624 source is the approved jump host, simple admin commands, change ticket |
| Monitoring / inventory tools using WMI | Consistent command line across many hosts, service account dedicated to the tool, regular schedule |
| Software deployment via PAExec / RemCom | Deployment server source, signed installer in the command line, maintenance window |

Scope exclusions to **account + source host + command pattern**. Never exclude `WmiPrvSE.exe` or `PSEXESVC.exe` as a parent outright.

## 6. Triage questions

- Does this account normally administer this host? Is it a service account being used interactively?
- What is the 4624 source? Is it a jump host or management server, or a user workstation?
- Does the command line carry the wmiexec `ADMIN$\__<epoch>` redirection?
- Is the PsExec payload a one-line admin command, or a script/binary dropped in a staging folder?
- What else ran on the target in the next hour: credential dumping, archiving, recovery tampering (HL-0002, HL-0007)?
- Is there a change record or ticket for the activity?

## 7. Operationalize

- Promote the Sigma rule with exclusions scoped to approved jump hosts and admin accounts; raise severity when the account is a service account or the command line contains `ADMIN$\__`.
- Add a companion rule on **System 7045** for services whose `ImagePath` points to `ADMIN$`, `%SystemRoot%\*.exe` with a random name, or `cmd.exe /c`.
- Restrict remote WMI (DCOM/135) and SMB admin shares to jump hosts via host firewall; enforce **LAPS** and tiered admin so a single cracked service account cannot log on everywhere.
- Deny network logon (`SeDenyNetworkLogonRight`) for service accounts that do not need it.
- Record outcome, detections, and data gaps in `templates/hunt-report.md` and `templates/intel-feedback.md`.

## Lab notes

- The lab covers five days of process and logon telemetry for a small domain. System 7045 is **not** included — reconstruct the movement from process and 4624 data.
- Expect two different remote-execution methods used by the intruder, on two different servers, and at least one admin look-alike you will need to explain using the logon source and account.
- Plenty of `WmiPrvSE.exe` activity is filtered out by the SCCM exclusion. Check that nothing malicious hides behind it.
- One of the PsExec-style hits launches something worth reading. Note its path — it reappears in another hunt.
- Not every hit has a type 3 logon right before it. Ask why, and what logon type you find instead.
