# Playbook HL-0010 — Exfiltration to Cloud Storage (rclone / MEGA)

| Field | Value |
|---|---|
| Hypothesis ID | HL-0010 |

| Tactic(s) | Exfiltration |
| Platforms | Windows servers (file, backup, database) and endpoints |
| Difficulty | Intermediate — requires telling sanctioned sync jobs from theft |
| Queries | [Sigma](../queries/sigma/hl-0010_exfiltration_to_cloud_storage.yml) · [KQL](../queries/kql/hl-0010_exfiltration_to_cloud_storage.kql) · [SPL](../queries/spl/hl-0010_exfiltration_to_cloud_storage.spl) |

## 1. Intelligence basis

Double-extortion ransomware operators steal data before they encrypt it, and the tool of choice is overwhelmingly **rclone** — an open-source, signed-looking, single-binary sync client that speaks to dozens of cloud providers. **MEGA** is the most common destination, with MEGAcmd as an alternative client. Typical tradecraft:

- rclone dropped into a staging folder (`C:\ProgramData\...`, `C:\Users\Public\...`) and **renamed** to something bland, but still carrying `OriginalFileName = rclone.exe` and the description *Rsync for cloud storage*.
- A **config file written by the operator** (`--config <path>\rc.conf`) holding the remote credentials, with a remote named after the provider (`mega:`).
- Performance and selection flags: `--transfers 16`, `--multi-thread-streams`, `--max-age 2y`, `--ignore-existing`, `--no-check-certificate`, `-q`.
- Run from a **file or backup server** with a cracked service account, shortly before encryption.

The same binary is also a legitimate IT tool, so the hunt is as much about **triage** as detection.

## 2. Hypothesis

> If an adversary is staging data for extortion in our environment, we expect **rclone (by name, OriginalFileName, description or flags) or MEGA command-line clients** performing `copy` / `sync` / `move` operations to **unsanctioned remotes**, and **sustained outbound connections from that process to MEGA or other cloud storage domains**, on servers holding sensitive data, during the last 14–30 days.

**Refuted if:** process and network telemetry cover ≥ 90% of in-scope servers for the window, and every rclone / MEGA execution is attributed to a documented job with a sanctioned remote, config path and service account.

## 3. Data sources

| Source | Event / table | Key fields |
|---|---|---|
| Sysmon | Event ID 1 (Process Create) | `Image`, `OriginalFileName`, `Description`, `CommandLine`, `ParentImage`, `User` |
| Sysmon | Event ID 3 (Network Connection) | `Image`, `DestinationHostname`, `DestinationIp`, `DestinationPort` |
| Windows Security | Event ID 4688 | `NewProcessName`, `CommandLine` — no OriginalFileName, so renamed rclone is caught only by its flags |
| Microsoft Defender XDR | `DeviceProcessEvents`, `DeviceNetworkEvents` | `ProcessVersionInfoOriginalFileName`, `ProcessVersionInfoFileDescription`, `RemoteUrl`, `RemoteIP` |
| Proxy / firewall / NetFlow | Session logs | Bytes out per destination — the true volume measure |

**Pre-check:** Defender XDR and Sysmon network events give **connection counts, not bytes**. If you need volume, confirm proxy or firewall logs with bytes-out are available. Without process telemetry carrying OriginalFileName, record renamed-binary coverage as a data gap.

## 4. Hunt steps

1. **Run the process query** (Query 1 / Search 1). It matches rclone by file name, OriginalFileName or description, rclone-style flags, and MEGAcmd binaries.
2. **Check for renaming.** Any row where `FileName` differs from `OriginalFileName` (the queries flag `IsRenamed` / `renamed`) is a priority lead — sanctioned jobs rarely rename the binary.
3. **Triage by remote name and config path.** The queries extract both:
   - Remote `s3corp:` with config under `C:\Program Files\rclone\` — fits a documented IT job.
   - Remote `mega:` (or any personal-cloud remote) with a config in `ProgramData`, `Users\Public` or `%TEMP%` — operator-built.
4. **Read the source path.** UNC paths to finance, HR or legal shares, or whole drive roots, indicate collection rather than a scoped export.
5. **Run the network query** (Query 2 / Search 2) for connections to `mega.co.nz`, `mega.nz` and `mega.io`, stacked per process. A burst of connections to many `userstorage` hosts over minutes is a bulk upload. Then widen to other providers your organization does not sanction.
6. **Pivot:**
   - How did the binary arrive? File creation in the staging folder, and the logon that preceded it (HL-0009, HL-0005).
   - Same account and staging folder on other hosts; impact activity that follows (HL-0007).
   - Proxy / firewall bytes-out for the destination IPs to size the loss.
7. **Classify** and record. Confirmed exfiltration is an incident — escalate immediately; legal and privacy timelines start now.

## 5. Known benign sources (tune, don't ignore)

| Source | How to recognize |
|---|---|
| IT-approved rclone jobs | Sanctioned remote name (e.g. `s3corp:`), config under `Program Files`, dedicated service account, fixed schedule, scheduler or service parent |
| Backup / DR replication | Documented destination bucket, same command line nightly, change record |
| Permitted MEGA desktop use | MEGAsync GUI client in a user profile, approved by policy — not MEGAcmd on a server |
| Developers testing rclone | Workstation, small data set, personal remote — still a policy conversation |

Write exclusions on **remote name + config path + account + host**, never on the `rclone.exe` file name.

## 6. Triage questions

- Which remote is the destination, and is it on the sanctioned list? Where does the config file live, and who wrote it?
- Is the binary renamed or running from a staging folder?
- What source path is being copied? Who owns that data and how sensitive is it?
- Which account ran it, and how did that account reach this host?
- How many connections, to how many destination IPs, over what period? What do proxy bytes-out say?
- Did encryption, recovery inhibition or other impact follow on the same hosts?

## 7. Operationalize

- Promote the Sigma rule with exclusions scoped to the sanctioned job (remote, config path, account, host).
- Block MEGA and unsanctioned cloud storage at the proxy for servers; alert on any server-originated connection to them.
- Application control: allow rclone only from its sanctioned path and signer; alert on OriginalFileName `rclone.exe` anywhere else.
- Feed destination IPs, remote names and staging paths back to CTI.
- Record outcome, detections created and data gaps in `templates/hunt-report.md` and `templates/intel-feedback.md`.

## Lab notes

The lab dataset contains process creation (Sysmon and `DeviceProcessEvents`) and network telemetry (Sysmon 3 and `DeviceNetworkEvents`) for this hunt. Network rows carry hostnames and IPs but no byte counts.

- Expect more than one rclone pattern. One is a recurring, documented job — you must be able to explain why it is benign rather than just excluding it.
- Do not search only for `rclone.exe` by name; the lab includes at least one copy that would slip past a file-name filter.
- Compare remote names, config paths, parents and accounts side by side; the difference is obvious once the columns are lined up.
- The network query tells you how much activity followed — use it to judge scale and timing against the rest of the intrusion.
