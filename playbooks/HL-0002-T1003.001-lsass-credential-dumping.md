# Playbook HL-0002 — LSASS Credential Dumping

| Field | Value |
|---|---|
| Hypothesis ID | HL-0002 |
| ATT&CK | **T1003.001** OS Credential Dumping: LSASS Memory · related: **T1218.011** System Binary Proxy Execution: Rundll32 |
| Tactic(s) | Credential Access, Stealth |
| Platforms | Windows endpoints and servers |
| Difficulty | Intermediate — requires PID resolution and renamed-binary reasoning |
| Queries | [Sigma](../queries/sigma/hl-0002_lsass_credential_dumping.yml) · [KQL](../queries/kql/hl-0002_lsass_credential_dumping.kql) · [SPL](../queries/spl/hl-0002_lsass_credential_dumping.spl) |

## 1. Intelligence basis

Dumping the memory of the Local Security Authority Subsystem Service (`lsass.exe`) is the most common way intruders turn one compromised host into domain-wide access. Ransomware affiliates and hands-on-keyboard operators routinely dump LSASS within hours of initial access, then crack or pass the harvested hashes and tickets. Tradecraft seen repeatedly in public reporting:

- **comsvcs.dll MiniDump** through `rundll32.exe` (`comsvcs.dll, MiniDump <PID> <file> full`, or by ordinal `#24`). Fully living-off-the-land: no tool is dropped, and the target is often given as a **PID**, so the string `lsass` never appears on the command line.
- **Sysinternals ProcDump** (`-ma lsass.exe`), frequently **renamed** (`pd64.exe`, `dump.exe`) and staged in `C:\ProgramData` or `%TEMP%` to dodge name-based detections.
- Task Manager "Create dump file", `sqldumper.exe`, `createdump.exe`, and custom tools that open a handle to LSASS and write a `.dmp` file.

Map this to your own PIRs by citing the specific report or advisory in your hypothesis card. Any credential-access finding should also raise the priority of HL-0005 (lateral movement) and HL-0006 (Kerberoasting) in the same window.

## 2. Hypothesis

> If an adversary has harvested credentials from LSASS memory in our Windows estate, we expect to see process-creation events whose command lines invoke **comsvcs.dll MiniDump**, **ProcDump-style full-memory flags against lsass**, or otherwise reference **lsass together with a `.dmp` output file**, frequently run from **renamed binaries, staging directories, or unusual user contexts**, in endpoint telemetry during the last 14–30 days.

**Refuted if:** process-creation telemetry (with command lines) covers ≥ 90% of in-scope hosts for the window, LSASS handle-access telemetry shows no unexplained high-privilege access, and every hit is attributed to a documented, change-controlled diagnostic or security tool.

## 3. Data sources

| Source | Event / table | Key fields |
|---|---|---|
| Sysmon | Event ID 1 (Process Create) | `Image`, `OriginalFileName`, `CommandLine`, `ParentImage`, `User` |
| Sysmon | Event ID 10 (Process Access) — optional, high value | `SourceImage`, `TargetImage`, `GrantedAccess`, `CallTrace` |
| Windows Security | Event ID 4688 (requires command-line auditing) | `NewProcessName`, `CommandLine`, `ParentProcessName` |
| Microsoft Defender XDR | `DeviceProcessEvents` | `FileName`, `ProcessVersionInfoOriginalFileName`, `ProcessCommandLine`, `InitiatingProcessFileName` |
| Microsoft Defender XDR | `DeviceEvents` (`ActionType == "OpenProcessApiCall"`) — optional | `FileName` (target), `InitiatingProcessFileName`, `AdditionalFields` |
| Sysmon / EDR | Event ID 11 / `DeviceFileEvents` | `.dmp` files created in staging paths |

**Pre-check:** confirm command-line capture is on and that you can resolve **PID to process name** on each host (Sysmon EID 1 `ProcessId`, `DeviceProcessEvents.ProcessId`). Without PID resolution the comsvcs variant cannot be confirmed. If neither command lines nor process-access telemetry exist, log the outcome as **Inconclusive (data gap)**.

## 4. Hunt steps

1. **Run the query** for your platform across the hunt window. Each row is labeled with a `DumpMethod` (comsvcs MiniDump, ProcDump-style flags, generic lsass + `.dmp`).
2. **Check for renamed tools.** Compare the on-disk file name with `OriginalFileName` / `ProcessVersionInfoOriginalFileName`. A ProcDump binary called anything other than `procdump*.exe`, or running from `C:\ProgramData`, `%TEMP%` or a user profile, is a strong signal by itself.
3. **Resolve the target PID.** For comsvcs hits the query extracts `TargetPid`. Look up which process held that PID on that host at that time (Sysmon EID 1 / `DeviceProcessEvents` for `lsass.exe`, or `tasklist` output in your EDR live-response history). LSASS PIDs are usually low and stable until reboot.
4. **Stack by tool, parent and account.** Sort ascending: a single execution by a standard user or service account from a script host (`powershell.exe`, `cmd.exe`, `wmiprvse.exe`) outranks anything run by your IR team from a jump host.
5. **Pivot** on suspicious hits:
   - The dump file path: was it created (Sysmon 11 / `DeviceFileEvents`), compressed, copied to a share, or exfiltrated?
   - Process access to LSASS on the same host (Sysmon 10 `GrantedAccess` `0x1010`, `0x1410`, `0x1fffff`; `OpenProcessApiCall`) to catch tools that never touch a command line.
   - Authentication from the same accounts in the hours after (4624 type 3/10, 4769) — dumped credentials are usually reused quickly (HL-0005, HL-0006, HL-0009).
   - What launched the dumper: walk the process tree back to initial access.
6. **Classify** each cluster as malicious, suspicious, or benign and record it in the hunt report. Treat any confirmed LSASS dump as a **credential compromise of every account logged on to that host** and escalate.

## 5. Known benign sources (tune, don't ignore)

| Source | How to recognize |
|---|---|
| Incident response / troubleshooting dumps | Named IR or admin account, jump host, matching ticket or change record, signed `procdump.exe` in a tools directory |
| ProcDump against other processes | Same flags, but the target is an application process (`w3wp.exe`, `sqlservr.exe`); not LSASS, so it should not match — if it does, your logic is too broad |
| Windows Error Reporting / crash handling | `WerFault.exe` parent, dump written under `C:\ProgramData\Microsoft\Windows\WER` after an actual LSASS crash |
| Security tooling | EDR or forensic collection agents; consistent signed parent across many hosts |

Each benign source should become a narrowly scoped exclusion (parent + account + host group), never an exclusion of `rundll32.exe` or `procdump.exe` as a whole.

## 6. Triage questions

- Does the command line target LSASS directly, or by PID? If by PID, which process owned it at that moment?
- Is the binary renamed or running from a user-writable or staging directory?
- Who ran it, from what parent, and is that account expected to hold `SeDebugPrivilege` on this host?
- Was the dump file later touched, compressed, copied off-host, or deleted?
- Do the accounts logged on to this host show new logons elsewhere shortly afterward?

## 7. Operationalize

- Promote the Sigma rule to production after scoping exclusions from step 5; consider raising it to **critical** on servers and domain controllers.
- Recommend enabling **LSA protection (RunAsPPL)** and **Credential Guard** where supported, and the Defender ASR rule *Block credential stealing from the Windows local security authority subsystem*.
- Recommend Sysmon EID 10 (or EDR process-access telemetry) filtered to `TargetImage` `lsass.exe` so tooling that avoids the command line is also visible.
- On a confirmed hit, trigger credential resets for every account cached on the host, including service accounts.
- Record outcome, detections created, and data gaps in `templates/hunt-report.md` and `templates/intel-feedback.md`.

## Lab notes

The lab dataset (`data/lab`) covers five days of "Northwind Labs" telemetry. For this hunt:

- The intruder used **more than one dumping method, on more than one host**. One of them never mentions `lsass` on its command line; you will need to explain why it is still an LSASS dump.
- Do not trust file names. Compare the image name with its original file name on every hit.
- The dataset also contains a legitimate, admin-run memory dump of a **different** process. Your query should not return it; if it does, revisit your logic.
- Set the lookback to cover early October 2026 (KQL `3650d`, SPL `earliest=0`).
