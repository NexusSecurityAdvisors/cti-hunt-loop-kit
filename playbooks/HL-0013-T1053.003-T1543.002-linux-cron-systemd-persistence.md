# Playbook HL-0013 — Linux Cron and Systemd Persistence

| Field | Value |
|---|---|
| Hypothesis ID | HL-0013 |

## 1. Intelligence basis

Ransomware affiliates no longer stop at Windows. Backup servers, NAS appliances and ESXi hosts hold the data that makes a victim pay, so affiliates move to them late in the intrusion, often over SSH with credentials harvested from the Windows side. Several ransomware families ship dedicated Linux and ESXi encryptors, and cryptomining crews use the same persistence tricks on exposed Linux servers. Recurring tradecraft:

- A line appended to **`/etc/crontab`**, dropped into **`/etc/cron.d/`** or written to a user spool (`/var/spool/cron/...`, `crontab -`) that runs every few minutes and **pipes a remote script to a shell** (`curl ... | sh`, `wget -O- ... | bash`).
- A **systemd unit** in `/etc/systemd/system/` (or `~/.config/systemd/user/` without root) with a **plausible name and description** (`dbus-cache`, `kworker`, `network-helper`) whose `ExecStart` points at a binary in **`/dev/shm`, `/tmp` or `/var/tmp`**, with `Restart=always`, followed by `systemctl enable --now`.
- Payloads staged in hidden directories under tmpfs (`/dev/shm/.x/`) so they disappear on reboot while the cron or unit re-fetches them.
- On ESXi, which has no systemd, the equivalent is editing `/etc/rc.local.d/local.sh` or the root crontab under `/var/spool/cron/crontabs/root`. Cover ESXi with its own log sources; this hunt's process telemetry is for general-purpose Linux and NAS.

Cite the specific advisory (for example a CISA #StopRansomware entry for a family with a Linux/ESXi encryptor) in your hypothesis card.

## 2. Hypothesis

> If an adversary has established persistence on our Linux servers or NAS appliances, we expect to see **shell commands that write cron entries or systemd unit files** whose payload **downloads, decodes or executes code from a staging path**, typically run **interactively over SSH as root on a single host**, in Linux process telemetry during the last 14–30 days.

**Refuted if:** process (or auditd execve) telemetry covers ≥ 90% of in-scope Linux hosts and NAS appliances for the window, FIM shows no unexplained changes to cron or systemd paths, and every hit maps to configuration management, a package script or a documented job.

## 3. Data sources

| Source | Event / table | Key fields |
|---|---|---|
| Sysmon for Linux | Event ID 1 (Process Create), Event ID 11 (File Create) | `Image`, `CommandLine`, `ParentImage`, `User`, `TargetFilename` |
| auditd | `EXECVE` / `SYSCALL` records; file watches, e.g. `-w /etc/cron.d -p wa -k cron`, same for `/etc/crontab`, `/var/spool/cron`, `/etc/systemd/system` | `exe`, `a0..aN`, `auid`, `key` |
| Microsoft Defender for Endpoint on Linux | `DeviceProcessEvents`, `DeviceFileEvents` | `FolderPath`, `ProcessCommandLine`, `InitiatingProcessFileName`, `AccountName` |
| File-integrity monitoring (AIDE, Wazuh, Tripwire, osquery `file_events`) | changes under `/etc/cron*`, `/var/spool/cron`, `/etc/systemd/system`, `/lib/systemd/system` | path, hash, owner, mtime |

**Pre-check:** NAS appliances and hypervisors frequently have **no agent at all**. List which in-scope hosts send process telemetry and which only send syslog. Note that the query only sees persistence written by a **shell command line**; a file dropped with `scp` or written by an editor shows up only in FIM or file-create events. Record uncovered hosts as **Inconclusive (data gap)** and use the live-response step for them.

## 4. Hunt steps

1. **Run the query** for your platform. It mirrors the Sigma rule: the command line must touch a cron or systemd path **and** carry a suspicious payload (`curl`/`wget`, `base64 -d`, `/dev/tcp`, `/dev/shm`, `/tmp`, `| sh`).
2. **Stack by persistence file, parent and account.** Sort by `Hosts` ascending: a write that happened once on one host is a lead; the same unit pushed to every server from `python3` (Ansible) or `ruby` (Puppet/Chef) is usually configuration management.
3. **Read the payload.** For cron, what runs and how often, and where does it fetch from (raw IP vs internal FQDN)? For systemd, what is `ExecStart`, does the name and `Description` imitate a system component, and is the binary in a tmpfs or hidden directory?
4. **Pivot on the host and time** (commented pivot query in the KQL file):
   - The session that wrote it: an `sshd` → `bash` login shortly before, and from which source IP (`/var/log/auth.log`, `journalctl -u ssh`).
   - Staging: `wget`/`curl` downloads into `/dev/shm` or `/tmp`, `chmod +x`, then `systemctl enable --now <unit>` or `systemctl daemon-reload`.
   - Execution: processes whose image is in `/dev/shm` or `/tmp`, or whose parent is `systemd`/`cron` and that you have never seen before; command lines with volume paths and new file extensions point at an encryptor.
   - Network: the fetch host from step 3 in proxy, firewall and DNS logs across the whole estate.
5. **Live response on flagged and uncovered hosts.** Run as root and save the output to the case:
   ```bash
   for u in $(cut -d: -f1 /etc/passwd); do echo "== $u"; crontab -l -u "$u" 2>/dev/null; done
   cat /etc/crontab; ls -la /etc/cron.d /etc/cron.hourly /etc/cron.daily /etc/cron.weekly /etc/cron.monthly
   ls -la /var/spool/cron /var/spool/cron/crontabs 2>/dev/null
   systemctl list-unit-files --type=service --state=enabled
   systemctl list-timers --all
   find /etc/systemd/system /lib/systemd/system /usr/lib/systemd/system /home/*/.config/systemd -newer /etc/hostname -type f -ls 2>/dev/null
   grep -rlE '/dev/shm|/tmp/|curl|wget|base64' /etc/cron* /var/spool/cron /etc/systemd/system 2>/dev/null
   ls -la /dev/shm /tmp /var/tmp; cat /etc/rc.local 2>/dev/null
   ```
   `-newer /etc/hostname` is a rough baseline; use a reference file whose mtime matches the last build or patch window. Compare unit files with the package database (`rpm -Va`, `debsums -c`) to find files no package owns.
6. **Classify** each cluster and record it in the hunt report.

## 5. Known benign sources (tune, don't ignore)

| Source | How to recognize |
|---|---|
| Configuration management (Ansible, Puppet, Chef, Salt) | Parent `python3`/`ruby`/`salt-minion`, staging dir such as `/tmp/ansible-tmp-*`, same unit on many hosts in a change window |
| Package maintainer scripts | Parent `dpkg`/`rpm`/`apt`, file name matches the package (`certbot`, `logrotate`), no download in the payload |
| Monitoring and heartbeat crons | `curl` to an **internal** health-check FQDN, documented owner, same schedule since it was created |
| Vendor NAS / appliance updates | Signed vendor update process, firmware change ticket, identical across appliances of the same model |

Scope exclusions to **parent + file path + destination** (for example Ansible writing `node_exporter.service`). Never exclude `curl` in cron as a whole — that is exactly the affiliate pattern.

## 6. Triage questions

- Was the write interactive (`sshd` → `bash`) or from automation? Who logged in, from where, and is root SSH even allowed?
- Does the cron fetch from a **raw external IP** or an internal FQDN you can attribute to an owner?
- Does the unit name or `Description` imitate a system component? Does a package own the file?
- Is `ExecStart` in `/dev/shm`, `/tmp` or a hidden directory? Does that binary still exist, and what is its hash?
- Is the same file present on one host or every host of that role? Is there a change ticket?
- What ran from the new unit or cron after it was enabled — and did anything touch the data volumes?

## 7. Operationalize

- Promote the Sigma rule with scoped exclusions from step 5. Add a high-fidelity variant: **any unit file whose `ExecStart` is under `/dev/shm`, `/tmp` or `/var/tmp`**, and any cron that pipes a fetch to a shell.
- Deploy **auditd watches** (or Sysmon for Linux / MDE) on cron and systemd paths for every Linux host, and get **NAS and hypervisor logs** off the box to a SIEM; most appliances support remote syslog.
- Mount `/tmp` and `/dev/shm` with **`noexec`** where workloads allow. Disable **root SSH login**, require keys plus MFA via a bastion, and keep NAS and ESXi management interfaces off user VLANs.
- Baseline enabled units and crontabs per server role (osquery `crontab` and `systemd_units` tables) and alert on drift.
- Record outcome, detections, and data gaps in `templates/hunt-report.md` and `templates/intel-feedback.md`.

## Lab notes

- The lab adds five days of Linux process telemetry for two servers (a NAS and a web server), as Sysmon for Linux JSON and as a Defender `DeviceProcessEvents` CSV. There is no FIM or auth log, so the live-response step is a tabletop exercise.
- Expect several cron and systemd writes. At least two are routine and need an owner and a reason before you set them aside; one of them runs on more than one host.
- Compare fetch destinations and `ExecStart` paths side by side — the difference between monitoring and an affiliate is in the details, not the keywords.
- One persistence-related command does not match the query at all. Use the pivot step to find what enabled the unit, what was staged before it, and what ran afterward.
- Note the time of the session and the fetch destination, then connect them to the Windows side of the intrusion: which earlier hunts share that infrastructure, and where could a root password for the NAS have come from?
