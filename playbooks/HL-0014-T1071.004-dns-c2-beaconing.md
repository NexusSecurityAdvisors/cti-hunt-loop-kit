# Playbook HL-0014 — DNS C2 Beaconing and Tunneling

| Field | Value |
|---|---|
| Hypothesis ID | HL-0014 |
| ATT&CK | **T1071.004** Application Layer Protocol: DNS · related: **T1572** Protocol Tunneling |
| Tactic(s) | Command and Control |
| Platforms | Windows endpoints, DNS servers |
| Difficulty | Advanced — needs timing statistics, not keyword matching, and a good sense of what normal DNS looks like |
| Queries | [Sigma](../queries/sigma/hl-0014_dns_c2_beaconing.yml) · [KQL](../queries/kql/hl-0014_dns_c2_beaconing.kql) · [SPL](../queries/spl/hl-0014_dns_c2_beaconing.spl) |

## 1. Intelligence basis

DNS is allowed out of almost every network, usually through the organization's own resolvers, so implants use it when HTTP egress is filtered or inspected. Commercial and open-source C2 frameworks (Cobalt Strike DNS beacons, Sliver, dnscat2, iodine) and many custom implants share the same traits:

- Each check-in encodes data or a session ID in a **long, high-entropy first label** (hex, base32 or base64-like) under an attacker-registered domain, so **every query name is unique** and resolver caches never answer it.
- Tasks come back in **TXT** (sometimes `NULL`, `CNAME` or `A`) responses.
- Check-ins are **periodic** — a sleep interval with some jitter — so the gaps between queries are far more regular than a human's.
- Parent domains are often **newly registered** and named to look like telemetry, CDN or update infrastructure.

Full tunneling (T1572) is the high-volume end of the same spectrum: thousands of queries per hour carrying a byte stream. Cite the report or advisory that motivates the hunt in your hypothesis card.

## 2. Hypothesis

> If an implant is using DNS for command and control in our estate, we expect to see **one host (and one process) querying many unique, long, encoded subdomains of a single parent domain at a regular interval** — low coefficient of variation of the inter-query time — often with **TXT** queries, in DNS server or endpoint DNS telemetry during the last 14–30 days.

**Refuted if:** DNS query logging covers all internal resolvers (and endpoint DNS covers ≥ 90% of in-scope hosts) for the window, direct external DNS is blocked, and every regular or high-cardinality parent domain maps to a known vendor service.

## 3. Data sources

| Source | Event / table | Key fields |
|---|---|---|
| Sysmon | Event ID 22 (DNSEvent) | `QueryName`, `Image`, `Computer`, `QueryResults` — the only source here that names the **process** |
| Windows DNS Server | Analytical / audit log; Sentinel `DnsEvents` (DNS connector or AMA) | `ClientIP`, `Name`, `QueryType`, `SubType`; `Computer` is the **DNS server** |
| Microsoft Defender XDR | `DeviceEvents` `ActionType == "DnsQueryResponse"` | `AdditionalFields.DnsQueryString`, `InitiatingProcessFileName` (sampled — weak for timing) |
| Network sensors | Zeek `dns.log`, Splunk Stream `stream:dns` | `query`, `qtype_name`, `id.orig_h`, answers |

**Pre-check:** confirm DNS query logging is on for **every** resolver and that clients cannot query external resolvers directly (firewall logs for UDP/TCP 53 and DoH endpoints leaving the network). Raw Sysmon 22 does not record the query type; TXT checks need server or network DNS logs. If the DNS server only logs `ClientIP`, you need DHCP or `DeviceNetworkInfo` to name the host. Record gaps as **Inconclusive (data gap)**.

## 4. Hunt steps

1. **Run the query** for your platform. Both group by **client (and process, in SPL) + registered parent domain** (last two labels; extend to three for suffixes such as `co.uk`) and drop reverse-lookup and internal zones.
2. **Read the statistics.** For each group the query computes query count, distinct names, the **mean and standard deviation of the gap between queries**, the **coefficient of variation (CV = stdev / mean)**, long-label share, TXT count and active hours. Human-driven lookups have a CV near 1 or higher; a sleeping implant with ±20% jitter sits near 0.1. The query only computes CV with at least 10 intervals.
3. **Rank.** Regular timing (CV ≤ 0.35) first, then lowest CV, then the highest **distinct-name ratio** (unique names / queries — near 1.0 means every query is new). Check `ClientsForDomain`: one client is an implant pattern, forty clients is usually installed software.
4. **Account for gaps.** Laptops sleep and implants change sleep time, which inflates the standard deviation. If a candidate has a moderate CV, split it by day or drop gaps longer than ~5× the median interval and recompute.
5. **Identify the host and process.** In `DnsEvents`, `ClientIP` is the querying host — map it through DHCP or `DeviceNetworkInfo`. Then run the SPL search (or query Sysmon 22 / Defender) for that host to get the `Image` behind the queries.
6. **Pivot:**
   - The process: path (user-writable `AppData`, `ProgramData`?), signer, parent, and how it persists (HL-0003, HL-0004).
   - The domain: WHOIS creation date, registrar, name servers, passive DNS and which other hosts ever resolved it.
   - Timing: when did beaconing start and stop, and what else happened on that host in the first minutes (process, network, logon events)?
7. **Classify** each cluster and record it in the hunt report.

## 5. Known benign sources (tune, don't ignore)

| Source | How to recognize |
|---|---|
| AV / EDR reputation look-ups over DNS | Signed security agent in `Program Files`, hash-like labels under the vendor's domain, **many hosts**, irregular timing that follows file activity |
| CDN, cloud and telemetry services with hashed host names | Parent domain belongs to a known provider, resolved by browsers and many hosts, mostly `A`/`AAAA`/`CNAME` |
| Update agents and NTP-like pollers | Regular timing but a **small, stable set of names**, known vendor domain, fleet-wide |
| Anti-spam / DNSBL and DKIM look-ups | Mail servers only, query names built from IPs or selectors |

Scope exclusions to **process + parent domain** (for example the signed AV agent querying its reputation zone). Do not allow-list a parent domain for every process: an implant can borrow a trusted-looking name.

## 6. Triage questions

- Which **process** is making the queries (Sysmon 22 `Image`)? Is it signed, and does it belong in that path?
- How regular is it — CV, mean interval, and does it run around the clock or only during working hours?
- What do the labels look like: length, character set, **entropy** (Shannon entropy above ~3.5 bits per character on 30+ characters is unusual for human-chosen names)? Does any label decode from hex or base32?
- What record types — **TXT** or `NULL` from a workstation is rare outside security tooling.
- How old is the parent domain, who registered it, and do its name servers host anything else?
- Is the parent domain a **known vendor**, and is it queried by one host or the whole fleet?

## 7. Operationalize

- Keep the Sigma rule as a low-severity pre-filter feeding the scheduled statistics query. Alert on **low-CV (≤ 0.35), high distinct-ratio (≥ 0.9) parent domains with long labels seen from one or a few clients**, with scoped vendor exclusions.
- Deploy **protective DNS / Response Policy Zones (RPZ)** on internal resolvers: block newly registered and newly observed domains, and known-bad feeds.
- **Block direct external DNS** (UDP/TCP 53, DoT 853) and unsanctioned DoH from clients; force all lookups through monitored resolvers.
- Turn on DNS query logging on every resolver and Sysmon 22 on endpoints, so host and process are both available.
- Record outcome, detections, and data gaps in `templates/hunt-report.md` and `templates/intel-feedback.md`.

## Lab notes

- The lab adds endpoint DNS (Sysmon 22, with the process) and the domain controller's DNS server log (`DnsEvents`, where `ClientIP` identifies the workstation). Map client IPs to host names with the IPs you have seen in the other lab tables.
- Most traffic is ordinary browsing to Microsoft, Google and internal names. Its CV should come out near 1 — use it to calibrate what "irregular" means.
- Expect one family of long, encoded-looking labels that is benign and seen across much of the fleet. You will need the process and the host count to explain it.
- Something else is very regular. Work out its interval, how long it ran, which process sent it, and how that process got onto the host.
