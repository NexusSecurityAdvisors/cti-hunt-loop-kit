# Playbook HL-0009 — RDP Lateral Movement

| Field | Value |
|---|---|
| Hypothesis ID | HL-0009 |
| ATT&CK | **T1021.001** Remote Services: Remote Desktop Protocol · related: **T1078** Valid Accounts |
| Tactic(s) | Lateral Movement · related: Stealth, Persistence, Privilege Escalation (T1078) |
| Platforms | Windows servers and endpoints (Active Directory domains) |
| Difficulty | Intermediate — requires knowing your admin paths and naming conventions |
| Queries | [Sigma](../queries/sigma/hl-0009_rdp_lateral_movement.yml) · [KQL](../queries/kql/hl-0009_rdp_lateral_movement.kql) · [SPL](../queries/spl/hl-0009_rdp_lateral_movement.spl) |

## 1. Intelligence basis

Once an intrusion has valid credentials, RDP is the quietest way to move: it is a built-in admin protocol, it blends with help desk and server administration, and it gives the operator a full GUI for browsing shares, running tools and staging data. Ransomware affiliates in particular follow a consistent pattern:

- Crack or dump a **service or admin account** (see HL-0002, HL-0006), then RDP with it — service accounts rarely have interactive logon restrictions applied.
- Pivot from the **first compromised workstation** straight to file, backup and domain servers, bypassing the jump hosts / PAWs that legitimate admins use.
- Touch **several servers in a short window** from the same source, often outside business hours.

Mature environments funnel all RDP to servers through a small set of jump hosts. That makes "RDP from anywhere else" a strong, low-volume hunt.

## 2. Hypothesis

> If an adversary is moving laterally with RDP in our environment, we expect successful **RemoteInteractive logons (Event ID 4624, LogonType 10)** whose source is **not an approved jump host**, especially by **service accounts** and from **workstations to servers**, during the last 14–30 days.

**Refuted if:** 4624 logon telemetry is collected from ≥ 90% of in-scope servers for the window, the jump-host list is current, and every remaining source/account/destination combination is attributed to a documented support or admin path.

## 3. Data sources

| Source | Event / table | Key fields |
|---|---|---|
| Windows Security | Event ID 4624 (LogonType 10 = RemoteInteractive) | `TargetUserName`, `IpAddress`, `WorkstationName`, `LogonType`, `Computer` |
| Microsoft Sentinel | `SecurityEvent` (EventID 4624) | `TimeGenerated`, `Computer`, `TargetUserName`, `IpAddress`, `LogonType`, `WorkstationName` |
| TerminalServices-RemoteConnectionManager | Operational Event ID 1149 | Network authentication succeeded — user and source IP, logged before session logon |
| TerminalServices-LocalSessionManager | Operational Event IDs 21 (logon), 25 (reconnect) | Session logon / reconnect with source address — survives some 4624 gaps |
| Microsoft Defender XDR | `DeviceLogonEvents` (`LogonType == "RemoteInteractive"`) | `AccountName`, `RemoteIP`, `RemoteDeviceName` |

**Pre-check:** confirm 4624 is collected from servers (not just domain controllers) and that `IpAddress` is populated. Network Level Authentication and RDP gateways can make the source appear as the gateway; know where yours terminates. If your jump-host list is unknown or stale, the hunt is **Inconclusive (data gap)** until it is fixed.

## 4. Hunt steps

1. **Set the allowlist.** Replace the `jumpHosts` placeholder (`10.10.5.10`) with your PAWs / bastions, and the host-name patterns with your naming convention or subnet ranges for workstations and servers.
2. **Run the query** for your platform across the hunt window.
3. **Stack source IP → account → destination.** Rare pairs sort first. Read each row as a sentence: "account X logged on interactively to server Y from host Z."
4. **Prioritize the flags** the queries compute:
   - **Service account** (`svc_` prefix) using RDP — service accounts should not log on interactively at all.
   - **Workstation → server** — user endpoints should not be an admin path to servers.
   - **Fan-out** — one source reaching several destinations in a short window.
5. **Pivot on suspicious sources:**
   - What else did the source host do around that time? Process creation, credential access (HL-0002), Kerberoasting (HL-0006), WMI / PsExec (HL-0005).
   - Logon type 3 from the same source and account immediately before the RDP session (share access, remote execution).
   - Activity inside the session on the destination: processes run by that account, files staged, tools dropped.
6. **Corroborate with 1149 / 21 / 25** where 4624 is missing or ambiguous.
7. **Classify** each cluster and record it in the hunt report.

## 5. Known benign sources (tune, don't ignore)

| Source | How to recognize |
|---|---|
| Help desk / remote support | Dedicated support hosts or subnet, support accounts, destinations are **workstations**, matches tickets |
| Admins bypassing the jump host | Named admin account, business hours, from an IT workstation — a process failure to fix, not to whitelist |
| Vendor / MSP remote access | Known gateway IP, named vendor accounts, change window |
| Console and loopback logons | `IpAddress` of `127.0.0.1`, `::1` or `-` (already filtered) |

Add confirmed support sources as **scoped** allowlist entries (source + account pattern + destination class), not as new jump hosts.

## 6. Triage questions

- Is the account a service, admin or standard user account? Should it ever log on interactively?
- Is the source an approved admin path? If not, who owns that host and was anyone at it?
- Is the destination a server class the account normally touches?
- Did the same source/account reach several hosts in minutes? Outside business hours?
- What happened on the source host in the hour before (phishing, credential theft, discovery)?
- What did the account do during the session on the destination?

## 7. Operationalize

- Promote the Sigma rule with your real jump-host list; keep it `low` on its own and raise severity in the SIEM when the service-account or workstation-to-server flag is set.
- Deny interactive / RDP logon for service accounts via GPO (*Deny log on through Remote Desktop Services*) and use gMSAs.
- Restrict inbound RDP to servers at the host firewall to jump-host addresses only.
- Feed confirmed lateral-movement paths back to CTI and the architecture team.
- Record outcome, detections created and data gaps in `templates/hunt-report.md` and `templates/intel-feedback.md`.

## Lab notes

The lab dataset contains 4624 logon events in `data/lab/security/security.jsonl` (Splunk) and `data/lab/sentinel/SecurityEvent.csv` (KQL). There is no TerminalServices or `DeviceLogonEvents` telemetry in the lab.

- The lab jump host is `10.10.5.10`; leave the placeholder as is. Admin RDP from it should disappear once the filter applies.
- After filtering, expect a short list. At least one recurring source is a benign look-alike you will need to explain.
- Read the account names and host-name prefixes carefully; the flags do most of the work, but you should be able to justify each verdict.
- When you find the suspicious source, check what that host was doing earlier in the timeline.
